### 2026-05-06 - 语音上传链路事故复盘

#### 背景
- 线上用户仍在通过旧 iOS 捷径向 `POST /api/voice` 上传语音。
- 为解决捷径等待时间过长的问题，曾临时引入 `/api/voice/init`、直传 Supabase、再异步处理的方案。
- 该方案改变了旧捷径的返回契约：旧流程原本返回转写文本，新流程返回 `signed_url/token/path/memo_id`，导致用户看到不可理解的返回内容。

#### 影响
- 临时 init 流程会先创建 `pending` 记录；如果后续上传或处理没有完成，会留下没有音频、无法转写的孤儿记录，并在网页上长期显示“转写中”。
- 固定 60 秒的讯飞转写超时与“按 40ms 一帧模拟实时发送”的实现冲突，接近 60 秒的音频存在被服务端自身超时掐断的风险。
- 这次排查中，用户承担了过多一线验证成本；开发侧没有在上线前充分回归旧捷径兼容性。

#### 修复
- 移除 `/api/voice/init` 和 `/api/voice/process`，恢复旧捷径只调用 `POST /api/voice` 的单接口契约。
- 对空转写和无效转写增加保护，避免 LLM 在没有有效 `raw_text` 时编造内容进入数据库。
- 对没有音频的陈旧 `pending` 记录，在网页展示为“上传未完成”，不再误显示“转写中”。
- 将讯飞转写超时改为动态超时：至少 60 秒，长音频按“音频时长 + 30 秒缓冲”计算。
- 增加 `npm run test`，覆盖 pending 孤儿记录识别和讯飞动态超时计算。
- 背面卡片增加明确的左上角翻回按钮，降低误触。

#### 经验教训
- 已上线接口和 iOS 捷径是生产合约；任何改动都必须保持向后兼容，或先新增并验证独立版本，不得直接改变旧入口语义。
- 生产数据不得随意删除或覆盖；遇到异常记录应先标记、解释、修展示，再由用户确认是否做数据修正。
- 涉及 Vercel、Supabase、讯飞、OpenRouter、iOS 捷径的改动，必须先列出可验证边界，再自测关键路径。
- 不能把首轮测试转嫁给用户；交付前必须说明实际跑过的测试、构建、线上探针和剩余风险。
- 新方案如果需要用户重配捷径，必须先证明旧方案的问题和新方案的必要性，不能在事故中临时扩大变更范围。

#### 回归要求
- 旧捷径：`POST https://voice2do.vercel.app/api/voice`，请求体为音频文件，返回中必须包含转写文本或明确错误，不能返回上传 token。
- 语音链路：覆盖空音频、无效转写、讯飞失败、音频保存失败、成功转写、网页展示、音频播放。
- 部署前：至少运行 `npm run test`、`npm run lint`、`npm run build`，并检查生产构建路由只暴露预期 API。
